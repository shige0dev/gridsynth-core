# GridSynth アーキテクチャ & モジュール設計指針
## Architecture & Modular Design Guidelines

本ドキュメントは、「**すべてにおいてコンセプトを統一して再利用性を最大化する**」ことと、「**共有のし過ぎ（過度な共通化）による複雑化・密結合・無駄を防ぐ**」ことを両立するためのGridSynth公式設計ガイドラインです。

---

## 1. コア設計思想：3層レイヤーアーキテクチャ

GridSynthのUIモジュールは、以下の**3つの独立したレイヤー**に厳格に分離して設計・実装します。

```
┌────────────────────────────────────────────────────────┐
│ 第3層: 独自UIモジュール (Composite)                     │
│   例: FMx3, SEQ8, SEQ16, MARKOV, KEYBOARD, PAT, CHORD  │
│   → 無理に共通化しない。独自の配置・操作感を持つ。        │
│   → ただし「部品（第1層）」だけを借りて組み立てる (合成) │
├────────────────────────────────────────────────────────┤
│ 第2層: 標準スキーマ駆動モジュール (Schema-Driven)       │
│   例: VCO, VCF, VCA, MIX, DELAY, CVDELAY, REVERB, LFO  │
│   → パラメータ定義 (min, max, step) の宣言だけで自動生成 │
│   → コード量は10〜30行で極小・バグの余地ゼロ             │
├────────────────────────────────────────────────────────┤
│ 第1層: 最小共通部品 (Primitives)                       │
│   例: CSS (48pxスライダ), bindScrubber, 端子ポート描画   │
│   → ポリシーを持たない「ただの素材」なので誰でも安全共有 │
└────────────────────────────────────────────────────────┘
```

---

## 2. 共有の境界線（やって良いこと・悪いこと）

### ✅ 徹底して共有すべきもの（第1層: Primitives）
- **物理規格**:
  - 縦型スライダの規格サイズ: **高さ 48px × 幅 14px**（`.native-vslider`）
- **操作系ヘルパー**:
  - 上下ドラッグによる高精度微調整: `UIHelpers.bindScrubber`
  - スライダ＋数値＋単位のHTML生成: `UIHelpers.createVSliderHTML`
  - スライダとスクラバーの同時紐付け: `UIHelpers.bindSlider`
- **描画系ヘルパー**:
  - 端子ポートの自動レイアウト: `UIHelpers.renderChassisPorts`
  - パネル上のバーメーター描画: `UIHelpers.renderPanelBars`

### ❌ 共有してはいけないもの（無理な共通化の禁止）
- **「何でもできる万能スキーマ」の作成**:
  - シーケンサのステップボタンや鍵盤、確率マトリクスを汎用スキーマエンジン（`schema`）に押し込もうとすると、スキーマ内に大量の特例フラグ（`isChord`, `isSeqStep`, `isKeyboard`）が増殖し、保守不能になります。
- **異種モジュール間のロジック共有**:
  - FMのオペレータ計算とADSRのエンベロープ計算など、異なる音楽ドメインのロジックを無理に1つの関数にまとめないでください。
  - 共通化は「同一ファイル内（例: `mod.js` 内の MATH1 と MATH2）」または「純粋な素材（`UIHelpers`）」に留めます。

## 3. モジュールの分類と適合基準

### A. 第2層【スキーマ駆動モジュール】
「スライダ数本＋モード切替ボタングループ」で完結するモジュールは、モーダルHTMLを手書きせず、`schema` を定義します。

- **該当モジュール**:
  - `VCO`, `SUB_VCO`, `NOISE`, `FOLD`
  - `VCF`
  - `VCA`, `MIX`, `SLIDER`
  - `DELAY`, `CVDELAY`, `REVERB`
  - `LFO`, `SH`
- **書き方のルール**:
  ```javascript
  export const VCF = {
      color: 'indigo',
      defaults: () => ({ ... }),
      ports: () => ({ ... }),
      schema: {
          color: 'indigo',
          groups: [ /* フィルタ種別等のボタングループ */ ],
          sliders: [ /* CUTOFF, RES(Q), CV MOD 等のスライダ定義 */ ]
      },
      renderGrid: (m) => `...`
  };
  ```

### B. 第3層【独自UIモジュール（コンポジション）】
鍵盤、シーケンス、マトリクス、キャンバス描画など、固有の操作体系を持つモジュールです。

- **該当モジュール**:
  - `FMx3`: 3オペレータの直列/並列アルゴリズム、カーブ選択
  - `SEQ8` / `SEQ16`: ステップごとのGate/CV/Activeボタン、ランタイム点灯
  - `MARKOV`: 確率マトリクス、自己遷移/各CHへの重み配分
  - `KEYBOARD`: ピアノロール鍵盤UI
  - `PAT`: ドラムパターンマトリクス
  - `CHORD`: 和音タイプ（8種）/ボイシング（4種）のグリッドボタングループ
  - `SCOPE`: オシロスコープ波形キャンバス描画
  - `CLK`: ゲート時間/クロック周期の動的クランプ表示バナー
  - `MATH` / `MATH2`: 数式・演算子ボタングループ
- **書き方のルール**:
  - `renderModal` と `bindEvents` は独立して記述する。
  - ただし、スライダには必ず **第1層の部品（`createVSliderHTML` / `.native-vslider`）** を使い、数値表示には **`bindScrubber`** を紐付ける。

---

## 4. 新規モジュール追加時のチェックフロー

```
新しいモジュールを作る場合:
  │
  ├─ Q1: 「スライダ数本 ＋ モード切替ボタン」だけで表現できるか？
  │    ├─ YES ➔ 【第2層: Schema駆動】で書く（renderModalは手書きしない）
  │    └─ NO  ➔ 【第3層: Composite】に進む
  │
  └─ Q2: 第3層で作る場合
       ├─ 独自HTMLを renderModal に書く
       ├─ スライダは必ず `createVSliderHTML` または class="native-vslider" (48px) を使う
       ├─ 数値ドラッグには `bindScrubber` を接続する
       └─ 他のモジュール用の特例コードを共通ファイルに混入させない
```
